## 1. Gate completion criteria

The gate is PASS only when all are true:

1. Data flows and data inventory are documented.
2. DPIA is completed/approved for the actual pilot processing.
3. Lawful basis is documented per processing purpose; any legitimate-interests use has a completed LIA.
4. Deployed AdGuard query logging/statistics/client-identification settings are directly verified and meet the required privacy posture.
5. Parent-facing privacy and protection-limit information is ready for use before activation.
6. ICO data-protection-fee applicability is assessed for the actual controller/legal entity.
7. Every processor/hosting/upstream recipient and any restricted international transfer is identified and reviewed; required processor terms/transfer safeguards are in place.
8. Recurring supporter payments remain disabled in Experiment 1; consumer-subscription obligations are re-checked only before that later payment test.

## 2. Proposed Experiment-1 data flow

### Setup/orchestration path

Parent browser → UseSafeWeb setup journey → temporary/pseudonymous experiment record.

Minimum inputs:
- participant ID generated by the experiment;
- child age band/stage, not date of birth;
- child device family (iPhone/Android);
- new vs already-used phone;
- one relevant service/app;
- completion state for each safety step;
- support/intervention minutes and reason;
- abandonment reason if applicable;
- comprehension responses for coverage gaps.

Do not collect by default:
- child name;
- exact date of birth;
- school;
- child email/phone;
- contacts;
- location;
- messages/photos;
- social usernames;
- browsing-history reports.

### DNS path

Child device → encrypted DNS endpoint / AdGuard-backed resolver → configured upstream DNS resolver → DNS response → child device.

Required design rule: DNS requests may be processed transiently to provide filtering, but identifiable query history is not a product feature and must not be persistently retained for the experiment unless an individually justified troubleshooting event requires the minimum necessary short-lived diagnostic data.

### Infrastructure/processor path

The actual hosting provider, server location, upstream resolver/provider, CDN/reverse-proxy provider (if any), email provider (if any), and any other processor/sub-processor are **UNVERIFIED** in the canonical repository and must be identified before PASS.

### Research/experiment record

Personal participant contact details, if needed for scheduling/follow-up, must be stored separately from technical/session metrics. GitHub must contain only aggregated or anonymised experiment results; do not store identifiable parent/child research records in this repository.

## 4. Lawful-basis map — provisional pending final controller/DPIA approval

This is a project compliance design, not legal advice.

### Core parent-requested setup and necessary child-linked DNS processing

**Provisional basis: UK GDPR Article 6(1)(f) legitimate interests**, subject to completion and approval of the LIA/DPIA for the actual environment.

Reasoning:
- legitimate interest: provide the parent-requested first-phone safety setup and baseline filtering, with the child’s safety/privacy as a primary design interest;
- necessity: minimal device/stage information and transient DNS processing are necessary to provide the selected service; persistent DNS history, behavioral profiling and advertising are not necessary and are excluded;
- balancing: the data subject is a child and therefore receives heightened protection. Mitigations are high-privacy defaults, no surveillance/history, no sale/advertising use, minimal identifiers, transparent parental controls, child-readable explanation, easy removal, and explicit protection gaps.

A formal LIA must record the three-part test and be approved with the DPIA before pilot activation. If the final service structure materially changes the processing or relationship, reassess the lawful basis rather than carrying this conclusion forward mechanically.

### Parent contact for scheduling/follow-up

Use only data necessary for the research relationship. Final basis depends on the actual recruitment/follow-up mechanism and must be documented before collection. Do not use research contact data for unrelated marketing.

### Security/abuse processing

Legitimate interests is a plausible basis for proportionate IT/security processing, but fields and retention must be established from actual technical need and included in the LIA/DPIA.

### Consent warning

Do not use consent as a generic substitute for necessity/accountability. ICO guidance confirms additional rules apply where an information-society service is offered directly to a child and consent is the basis, including parental authorisation for children under 13. The current product is parent-led; any later direct child account/service would require a fresh assessment.

## 5. LIA — core processing draft

### Purpose test

UseSafeWeb has a legitimate interest in providing a parent-requested safety setup and DNS filtering that reduces exposure to selected harmful/inappropriate domains while coordinating native safeguards. The child also has interests in safety, privacy, agency, and freedom to access lawful information.

### Necessity test

Necessary:
- device/stage/service routing inputs;
- processing DNS requests to resolve/filter them;
- minimal technical data needed for security/reliability;
- pseudonymous experiment metrics needed to decide whether the product should exist.

Not necessary and therefore prohibited for Experiment 1:
- persistent identifiable browsing/DNS history;
- child behavioral profiles;
- message/location/contact data;
- targeted advertising;
- sale of family data;
- broad engagement analytics unrelated to the validation hypothesis.

### Balancing test

Risk is elevated because the data subject is a child and DNS activity can reveal sensitive interests. The balance is acceptable only if the product remains transparent and non-surveillance, logging is minimised, the child is not profiled, controls are proportionate, the parent deliberately enables the service, the child can receive an age-appropriate explanation, removal is straightforward, and processor/transfer safeguards are verified.

**Draft LIA outcome:** provisionally supportable, but NOT APPROVED until actual logging, processor, transfer and retention facts are verified and incorporated.

## 7. Mandatory DNS privacy configuration for Experiment 1

AdGuard Home supports query logging, file logging, statistics, client IP anonymisation, and per-client query-log/statistics exclusions. Its technical documentation states query logs can contain domain names and client IP/searchable client information.

Experiment-1 requirement:

1. persistent query logging for participant child devices: OFF;
2. file query logging for participant child devices: OFF;
3. identifiable per-client statistics: OFF/excluded unless a specific aggregate measure is proven necessary and non-identifying;
4. client IP anonymisation: ON where any operational log/statistic can still contain client addresses;
5. no parent-facing browsing-history or top-domain report;
6. diagnostic logging, if exceptionally enabled, is time-boxed, purpose-specific and deleted immediately after the incident is resolved;
7. do not enable WHOIS/rDNS/client-enrichment solely for product analytics.

**Operational status: UNVERIFIED.** No deployed AdGuard configuration is present in the canonical repository, and no prior verified environment facts were recoverable.

## 8. Parent-facing privacy and coverage notice — minimum content

Before activation, state plainly:

- UseSafeWeb helps configure phone/service safeguards and provides baseline domain-level filtering.
- DNS requests must be processed to answer/filter them, but the service is not designed to create a browsing-history product.
- It does not read private messages, track location, inspect social feeds, or guarantee complete online safety.
- Some harmful material inside apps/services is outside DNS-level protection.
- Native/platform settings confirmed by the parent are labelled parent-confirmed; only system-observable protection is labelled verified.
- Explain what experiment information is collected, why, retention, who receives it, and how the parent can withdraw from the research/service or request deletion where applicable.
- Provide an age-appropriate child explanation that filtering is present and what it does/not monitor.

Do not claim “no logs” until deployed settings and every relevant processor/upstream are verified.

## 9. ICO data-protection-fee assessment

ICO guidance states controllers generally must pay the data-protection fee unless an exemption applies. Current tiers are £52, £78, and £3,763; Tier 1 applies to micro-organisations with maximum turnover £632,000 or no more than 10 staff, subject to the rules/exemptions.
