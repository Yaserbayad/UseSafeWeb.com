## 1. Purpose and acceptance boundary

This matrix binds every High/Critical control path in the current accepted TSK-0485 end-to-end threat model to an implementation owner, current design/config authority, implementation target, verification method, release gate, monitoring path, failure response and current status.

It is an **implementation/verification control map**, not proof that downstream software or production controls already exist. A control is release-satisfied only when the downstream implementation and verification evidence named here passes in the correct environment and gate.

Under DEC-0056/CR-0009, the legal-only predecessor TSK-0240 is `OWNER_EXTERNAL_SATISFIED` for governed dependency/gate sequencing. TSK-0240 remains planning-DEFERRED/WAITING for traceability and is **not** represented here as legal PASS, compliance evidence, approval, waiver, exemption, filing or attestation. Mixed privacy/security work remains fully in scope: data minimisation, no-history enforcement, ownership isolation, deletion/recovery mechanics, vendor technical behavior, logging/telemetry controls, tests and release evidence remain mandatory.

## 3. Status and gate semantics

- **DESIGN_BOUND / IMPLEMENTATION_PENDING** — the current design/control authority exists, but L6 implementation and required negative/runtime evidence are still required.
- **CONFIG_BASELINE_BOUND / RUNTIME_REVERIFY** — a versioned configuration baseline exists, but release/runtime inspection remains mandatory.
- **OWNER_EXTERNAL / NOT_AI_VERIFIED** — legal/regulatory/compliance conclusion is outside AI scope under CR-0009; this is not legal evidence and never substitutes for technical privacy/security evidence.
- Every Critical/High row below is blocking at **LG-08 and/or LG-09** until its named implementation/test evidence passes. No row may be closed merely because this matrix exists.

## 5. Cross-cutting control ownership and release rules

1. **Authorization:** server-side, per-object/per-action, deny by default. Authentication, opaque IDs and ClientID never substitute for ownership authorization.
2. **Protection truth:** account/device registration, configuration presence and parent confirmation remain weaker evidence than current technical verification; stale/failed verification downgrades state.
3. **No-history privacy:** persistent identifiable query/file logging and identifiable per-client statistics remain OFF/excluded. No telemetry, cache, backup, debug path or product datastore may create browsing/domain history.
4. **Secret boundary:** no production secret/token/private key in Git, browser bundles, durable evidence or logs. Runtime injection must be scoped, revocable and auditable.
5. **Partial failure:** ambiguous non-idempotent effects stop progression until reconciliation proves one safe durable state.
6. **Recovery:** clean-server recovery and rollback cannot resurrect deleted/revoked authorization or prohibited data.
7. **Supply chain:** untrusted PR/dependency/action content cannot inherit protected secret/write/deploy authority.
8. **Monitoring:** TSK-0539 must bind every actionable SLI/threat signal to fields, retention, access, threshold and runbook without DNS/domain history; later alert routing/runbooks cannot weaken this matrix.
9. **Implementation backlog:** TSK-0048 must assign each row to a bounded vertical implementation/test slice with exact repository/config location. Until then, the logical implementation target in this matrix is authoritative and the physical path is intentionally not invented.
10. **Independent acceptance:** security/privacy/recovery rows require evidence independent of the producer where their current acceptance/risk requires it. TSK-0518 defines this explicitly for recovery; the master verification plan must preserve equivalent independence for material security/privacy boundaries.

## 6. CR-0009 legal-scope treatment

- Legal/regulatory/compliance determinations are owner-external and are not part of this matrix's PASS claim.
- TSK-0240 is used only as `OWNER_EXTERNAL_SATISFIED` sequencing under DEC-0056/CR-0009. It remains DEFERRED/WAITING in WBS/runtime records and is not legal evidence.
- Any future legal conclusion that contradicts a technical design must be treated as higher-authority current reality and can reopen affected technical work; this matrix cannot waive a known prohibition.
- `RSK-0001` legal/privacy-readiness risk is not closed by TSK-0239. Technical privacy controls remain mandatory regardless of legal-scope ownership.
