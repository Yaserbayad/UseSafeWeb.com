## 1. Purpose and authority boundary

This document defines the current end-to-end security and abuse threat model for the approved Version-1 UseSafeWeb.com architecture: the complete accountless web/setup/protection journey plus the optional parent account/session, minimum parent/device ownership persistence and lightweight dashboard/device-management surface. It is a **security design and release-condition artifact**, not proof that downstream controls are implemented or tested.

The model preserves the current canonical boundaries:

- core value remains usable without authentication;
- optional parent authentication/account ownership never substitutes for technical protection verification;
- only fresh qualifying technical evidence may produce `protected_verified`;
- `ClientID` is an opaque DNS-control reference and is never authentication or authorization;
- AdGuard administration credentials and raw administration interfaces remain server-side and non-public;
- persistent identifiable DNS query/file logging remains OFF and identifiable per-client statistics remain OFF/excluded;
- no browsing/query/activity-history product store, child account or unrestricted customer DNS administration is introduced;
- J0/J1 anonymous journey state remains separated from AUTH/A account state, with no automatic anonymous-to-account linkage;
- AI action authority remains independent of infrastructure/server privilege;
- `RSK-0001` remains OPEN and `INT-0007` runtime/configuration/data-flow reality remains a downstream verification boundary;
- no real participant, production processing, public launch, staffing, legal conclusion, LG-07/LG-08/LG-09 PASS or downstream task PASS is inferred here.

Under `INT-0015`, an exploitable **Critical or High** path on the active release surface is release-blocking until the applicable prevention, detection and recovery controls are implemented and the specified blocking verification passes. This model may define those controls; it cannot self-certify their implementation.

## 2. Method and severity

The model applies a trust-boundary/asset/abuse-case review with STRIDE-style prompts (spoofing, tampering, repudiation, information disclosure, denial of service and elevation of privilege) to every active external boundary. Current official OWASP and GitHub security guidance is used as supporting engineering reference, while the project WBS/registers/runtime remain project authority.

Severity is project-impact based:

| Severity | Meaning | Release disposition |
|---|---|---|
| **Critical** | Plausible compromise can create cross-parent/admin privilege, prohibited browsing/query-history exposure, materially false protection status, broad DNS/admin compromise, destructive unrecoverable control loss, or broad resolver abuse/cost exhaustion. | Blocking until implemented control + blocking verification pass. |
| **High** | Plausible exploit can materially compromise a parent/session/device, integrity, availability, privacy or security boundary without the broader Critical consequence. | Blocking until implemented control + blocking verification pass. |
| **Medium** | Material but bounded weakness with no demonstrated High/Critical path under the current architecture. | Must have owner/disposition before release; can be non-blocking only with evidence. |
| **Low** | Limited-impact hardening issue. | Track and verify proportionally. |

A design control being listed below means **CONTROL PLAN DEFINED; IMPLEMENTATION/RETEST REQUIRED** unless a separate current accepted task provides direct implementation evidence.

## 3. Assets, actors and trust boundaries

### 3.1 Protected assets

1. Truthful Protection Map and safeguard-routing state, especially `protected_verified`.
2. Parent identity/session and authorization state.
3. Parent-to-device ownership mapping and opaque device identifiers.
4. Server-only AdGuard `ClientID` mapping and administration credentials.
5. DNS endpoint availability and configuration integrity (`dns.usesafeweb.com`, DoH `/dns-query`).
6. J0/J1 anonymous journey state and its expiry/non-linkage guarantees.
7. Minimum persistent A-domain parent/device settings/lifecycle data.
8. Account/device deletion, revocation and recovery state.
9. Application source, dependencies, CI/CD workflows, deployment credentials and infrastructure secrets.
10. Privacy-safe operational events/alerts and evidence integrity.
11. Public domain/TLS/DNS routing and recovery capability.

### 3.2 Threat actors / failure agents

- unauthenticated Internet attacker or automated scanner;
- malicious or compromised authenticated parent account;
- attacker with a stolen/fixed/replayed parent session;
- compromised parent browser/device or hostile extension/script context;
- abusive resolver client, botnet or cost-exhaustion actor;
- compromised dependency, package registry, GitHub Action or build artifact;
- compromised/mis-scoped CI, deployment, server or administration credential;
- malicious/accidental operator or AI automation acting beyond authority;
- authentication/provider/datastore/upstream DNS outage or compromise;
- network/VPN/browser-specific resolver behavior that bypasses the intended DNS path;
- concurrency, partial failure, retry, restore or migration fault creating stale/inconsistent security state.

### 3.3 Trust boundaries

- **TB-WEB:** Internet/browser ↔ public Next.js web/application surface.
- **TB-ANON:** browser ↔ J0/J1 anonymous journey/configuration/verification state.
- **TB-AUTH:** browser ↔ optional authentication/session boundary.
- **TB-OWN:** authenticated parent ↔ parent/device ownership and persistent A-domain state.
- **TB-ADG:** application server ↔ typed/allowlisted AdGuard control boundary.
- **TB-DNS:** Internet/client resolver ↔ encrypted DNS endpoint/upstream resolution path.
- **TB-OPS:** service/runtime ↔ logs, metrics, alerts, recovery and administrative operations.
- **TB-CI:** source/PR/dependency/action ↔ CI/CD/build/deployment credentials and artifacts.
- **TB-EXT:** application ↔ authentication provider, datastore, DNS/upstream and other approved providers.
- **TB-REC:** live state ↔ deletion, backup/restore, rollback and disaster-recovery paths.

## 5. High/Critical control and release-blocking rules

The catalogue contains explicit prevention, detection, recovery and blocking verification for every High/Critical path. The following global rules apply:

1. **No exploitable Critical/High open path may be released merely because this threat model exists.** The applicable downstream implementation and negative/security tests must pass.
2. **Authorization is per object/action, server-side and deny-by-default.** Authentication alone, opaque IDs or `ClientID` do not authorize a device operation.
3. **Session failure is fail-closed for account-only operations; accountless core remains independent.** Provider/datastore failure cannot grant authority or silently convert core value into mandatory login.
4. **Protection truth is fail-safe.** A lost, stale, conflicting or tampered verification path downgrades the protection state; it never preserves `protected_verified` by assumption.
5. **AdGuard administration is not a customer API.** Public/browser access, arbitrary `/control` passthrough and browser-held administration secrets are release blockers.
6. **DNS abuse is a Critical availability/cost threat.** Controls must constrain abuse/amplification/resource/cost exhaustion while preserving intended supported clients.
7. **No-history privacy is a security control.** Any persistent identifiable DNS/domain browsing history, identifiable per-client statistics or unapproved account/anonymous linkage is release-blocking.
8. **Supply chain and CI/CD are production trust boundaries.** Untrusted code/PR/dependency/action content cannot inherit write/deploy/secret authority by default.
9. **Deletion/recovery is an authorization boundary.** A partial delete, restore or retry cannot resurrect access or silently leave an orphan privileged control reference.
10. **Technical privilege never creates owner authority.** Root, CI write or administration capability cannot override WBS Action Authority or frozen owner decisions.

## 6. Required downstream verification mapping

This model intentionally reuses existing WBS verification work rather than creating a duplicate security program.

| Control family | Primary downstream verification path / condition |
|---|---|

| AdGuard allowlist/admin isolation | TSK-0410 design then TSK-0495 and TSK-0264 negative/runtime evidence. |

| Supply chain/CI/CD | TSK-0489/0491/0492 plus actual committed lockfile/action/workflow evidence. |
| Anonymous J0/J1 threats | Current TSK-0487 design plus implementation/security tests; no account-linkage regression. |
| Browser/device/network/protection truth | Current TSK-0409, TSK-0517 and TSK-0320 invariants plus implementation/runtime tests. |

A downstream task may satisfy a row only through its own current acceptance evidence. Historical artifacts, source existence or this model cannot substitute for that proof.

The following are **not defects in threat-model coverage**, but they prevent this L5 design from being represented as implemented security:

- `TSK-0356` authentication/server-session architecture is not yet PASS; exact provider/session implementation controls remain downstream.
- `TSK-0232` parent/device ownership authorization model is not yet PASS.
- `TSK-0410` typed/allowlisted AdGuard adapter and ClientID lifecycle contract is not yet PASS.
- production observability, alert routes and runbooks are not yet fully implemented/rehearsed; TSK-0238 records this gap.
- exact production datastore/runtime/backup implementation remains downstream.
- `INT-0007` still requires inspection of actual runtime/configuration/schema/log/cache/recipient/backup/deletion reality before release.
- `RSK-0001` remains OPEN; this security model makes no final legal/privacy-compliance determination and does not authorize real England participant activation.
- TSK-0240 remains planning-DEFERRED under its current trigger; no DPIA/LIA conclusion is inferred here.

If later implementation introduces a new public endpoint, new persistent field, new provider, file upload, user-influenced server-side URL fetch, new administration capability or new trust boundary, TSK-0485 must be reviewed/reopened as appropriate before the new surface can rely on this model.
